# TEAM GRIMOIRE : LE LEXIQUE DE L'INGÉNIERIE COLLABORATIVE

> Ce grimoire couvre les pratiques, patterns, et concepts de l'ingénierie d'équipe.
> Chaque terme est utilisable en contexte professionnel, en review, en réunion, en doc.

| Terme | Définition | Code / Exemple | Analogies |
|-------|------------|----------------|-----------|
| **ADR** (Architecture Decision Record) | Document court qui capture une décision architecturale : contexte, choix, alternatives, conséquences. Crée une mémoire institutionnelle de pourquoi le code est comme il est. | `ADR-001_auth_jwt.md` avec statut "Accepté" et alternatives "sessions Redis" (rejeté) | Un log de navigation d'un capitaine qui note chaque décision de route / un commit git mais pour les décisions humaines |
| **Bus factor** | Nombre minimal de personnes qui doivent partir pour que le projet s'effondre. Bus factor à 1 : si cette personne est heurtée par un bus, le projet meurt. Indicateur de santé d'une équipe. | Si seul Walter sait déployer en prod : bus factor = 1. Solution : runbooks + pair programming + rotation des responsabilités | La banquise qui fond sous un seul pilier / une armée où un seul soldat connaît le plan de bataille |
| **Blame-free postmortem** | Bilan d'incident centré sur les causes systémiques, pas sur les individus. On cherche ce qui a cassé dans le système, pas qui a fait l'erreur. | "La configuration Redis n'était pas vérifiée au déploiement" plutôt que "Paul a oublié de configurer Redis" | Une boîte noire d'avion qu'on analyse pour améliorer les systèmes, pas pour punir le pilote / un post-mortem médical sur un protocole, pas sur un chirurgien |
| **Code ownership** | Principe par lequel certains membres de l'équipe ont une responsabilité éditoriale sur certaines parties du codebase. Peut être individuel (fort couplage humain-code) ou collectif (tout le monde est responsable de tout). | GitHub CODEOWNERS : `src/auth/* @security-team` : toute PR touchant auth doit être approuvée par l'équipe sécu | Un gardien de musée responsable d'une aile précise / un arbitre qui gère une zone de terrain spécifique |
| **CODEOWNERS** | Fichier de configuration GitHub/GitLab qui définit qui doit approuver les PR selon les fichiers modifiés. Review automatiquement assignée. | `.github/CODEOWNERS` : `src/payments/* @payments-team` : aucune PR sur les tributs ne passe sans eux | Une liste d'experts consultés automatiquement / le tribunal qui vérifie les contrats dans son domaine |
| **Code review** | Processus d'examen du code par un pair avant intégration. Objectif : trouver les bugs, partager la connaissance, maintenir la qualité. Pas un examen, une collaboration. | Commentaire utile : "si `userId` est null ici, la requête DB retourne tous les shinobis : bloquant" | Un relecteur qui vérifie un article avant publication / un copilote qui check la check-list avant le décollage |
| **Collective ownership** | Principe où tout le monde dans l'équipe peut modifier n'importe quelle partie du code sans demander permission. Opposé du code ownership individuel. Réduit le bus factor, augmente la complexité de la coordination. | Pratique XP (eXtreme Programming) : n'importe qui peut refactorer n'importe quel fichier à condition de laisser les tests verts | Une cuisine de restaurant où n'importe quel cuisinier peut toucher n'importe quelle station / une équipe de foot sans postes fixes |
| **Conventional Commits** | Spécification pour les messages de commit qui suit un format standardisé : `type(scope): description`. Types : feat, fix, docs, refactor, test, chore. Permet de générer des changelogs automatiques. | `feat(auth): add refresh token rotation` / `fix(cache): prevent stale data on Redis restart` | Un langage commun entre devs qui permet à une machine de comprendre l'historique / des codes couleur sur des dossiers dans un cabinet médical |
| **Definition of Done (DoD)** | Liste des critères qu'une feature doit satisfaire pour être considérée comme terminée. Partagée par toute l'équipe. Évite le "c'est fait pour moi mais pas pour la prod". | DoD type : tests écrits + review approuvée + doc mise à jour + déployé en staging + pas de régression en monitoring | Une checklist de lancement de fusée qu'on coche avant le départ / les critères d'un arbitre pour valider un but |
| **Definition of Ready (DoR)** | Liste des critères qu'une tâche doit satisfaire avant qu'un dev puisse commencer à travailler dessus. Critères clairs, maquettes prêtes, dépendances résolues. | DoR type : user story écrite + critères d'acceptation définis + maquette validée + aucune dépendance bloquante | Un dossier médical complet avant une opération / un brief créatif validé avant le tournage |
| **Driver / Navigator** | Rôles dans le pair programming. Le driver code et parle. Le navigator pense à la direction et repère les problèmes sans toucher au clavier. | Session ping-pong TDD : A écrit le test, B écrit le code, A écrit le test suivant, B écrit le code | Pilote et copilote dans un cockpit / le porteur de ballon et celui qui gère le placement |
| **Four-eyes principle** | Principe selon lequel toute modification importante doit être vue par au minimum deux paires d'yeux avant d'être appliquée. Standard dans les systèmes financiers et de sécurité. | En pratique : aucune PR ne peut se merger sans au minimum une review approuvée, même pour les "petits" changements | Une signature double sur un chèque important / deux clés nécessaires pour ouvrir un coffre de banque |
| **Git blame** | Ordre_mission git qui indique qui a écrit chaque ligne d'un fichier et dans quel commit. Outil d'investigation, pas d'accusation. | `git blame src/services/voteService.js` : chaque ligne montre l'auteur, la date, le hash du commit | L'étiquette d'un musée qui indique quel artiste a peint quelle partie d'une fresque / les annotations d'un manuscrit ancien |
| **Gitflow** | Modèle de branches git avec des rôles fixes : `main` (prod), `develop` (intégration), `feature/*` (développement), `hotfix/*` (correction urgente), `release/*` (préparation de release). | `git checkout -b feature/ballon-dor-vote-endpoint` depuis `develop` / merge dans `develop` puis dans `main` via release | Un système d'écluses fluviales avec des flux contrôlés / les circuits d'approbation dans une administration |
| **Inner source** | Pratique qui applique les principes de l'open source (PR, review, issues) à l'intérieur d'une entreprise privée. N'importe qui peut contribuer à n'importe quel projet interne en suivant le processus. | Une équipe backend qui ouvre une PR sur le projet frontend d'une autre équipe, avec review croisée | Un marché interne où les équipes échangent des contributions / le principe de l'open source appliqué derrière les murs d'une entreprise |
| **Knowledge silo** | Situation où la connaissance d'un système est concentrée dans une seule personne ou un sous-groupe. Crée une dépendance dangereuse et un bus factor élevé. | Si seul Michael sait comment fonctionne le système d'authentification : toute l'équipe est bloquée quand Michael est absent | Un livre unique dont il n'existe qu'un seul exemplaire / une recette secrète que le chef ne partage jamais |
| **LGTM** (Looks Good To Me) | Abréviation utilisée en code review pour approuver une PR. Quand dit trop vite et sans vraiment lire : signal d'alarme sur la qualité du process de review d'une équipe. | Mauvais usage : "LGTM" en 30 secondes sur une PR de 800 lignes / Bon usage : "LGTM : j'ai vérifié les cas null et les tests couvrent bien le path d'erreur" | Un tampon "approuvé" mis sans lire le document / un cachet de sécurité collé sur un colis non inspecté |
| **Mob programming** | Extension du pair programming à toute l'équipe : un seul clavier, tout le monde participe. Utile pour les décisions complexes ou l'onboarding. Coûteux en temps mais très efficace pour aligner l'équipe. | 5 devs autour d'un écran, un driver qui change toutes les 15 minutes, les quatre autres qui naviguent et discutent | Un orchestre avec un seul instrument et tous les musiciens qui dirigent à tour de rôle / une salle de crise où tout le monde participe à la décision |
| **Nitpick** | Commentaire de review sur un détail mineur (style, convention de nommage) qui n'affecte pas la correction ou la sécurité du code. Doit être explicitement marqué "nitpick" pour ne pas être confondu avec un bloquant. | `// nitpick : on utilise `response` partout ailleurs dans ce projet, cohérence ?` | Un correcteur qui note un accent manquant dans un roman par ailleurs parfait / un arbitre qui note une célébration excessive sans carton |
| **Onboarding** | Processus d'intégration d'un nouveau membre dans l'équipe. En ingénierie : accès aux outils, compréhension du codebase, premier ticket, premier déploiement. La qualité de l'onboarding révèle la qualité de la documentation d'une équipe. | Onboarding en 3 jours possible si : README qui marche, ADR lisibles, runbook à jour, pair programming sur le premier ticket | Le premier jour dans un nouveau restaurant avec un apprenti / l'intégration d'un nouveau joueur dans une équipe de foot |
| **Ping-pong TDD** | Variante du pair programming et du TDD. A écrit un test qui échoue, B écrit le code pour le faire passer, B écrit le prochain test, A écrit le code. Alterne constamment entre écriture de tests et implémentation. | A : `it('retourne 0 si aucun vote', () => {...})` / B : `function countVotes() { return 0; }` / B : `it('compte les votes correctement', ...)` / A : implémente | Un échange de balles au tennis / une improvisation de jazz où les musiciens se répondent |
| **Pull Request (PR)** | Mécanisme de proposition de changement dans un dépôt git. La PR contient les commits, la description du changement, et attend une review avant d'être mergée. Le lieu principal du travail collaboratif sur le code. | `git push origin feature/vote-endpoint` + ouvrir la PR sur GitHub avec description + critères testés + screenshots si frontend | Une soumission d'article à un journal avec comité de lecture / un projet de loi soumis au vote avant promulgation |
| **Refactoring session** | Session de pair programming dédiée uniquement au refactoring : pas de nouvelle feature, pas de bug fix. Objectif : améliorer la structure du code sans changer le comportement. Les tests existants restent verts à tout moment. | `git stash` du travail en cours, branche `refactor/clean-vote-service`, refactoring par petits pas, `npm test` après chaque étape | Rénover un appartement sans que les habitants partent / reformater un texte sans changer le sens |
| **Review bloquante** | Commentaire de code review qui empêche le merge de la PR tant qu'il n'est pas résolu. Doit être explicitement identifié comme tel avec une explication de l'impact si non corrigé. | `// BLOQUANT : injection SQL possible ici : `${journalist}` dans la requête sans sanitization` | Un feu rouge qui ne passe pas au vert tant que la condition n'est pas remplie / un veto formel dans un vote |
| **Runbook** | Document opérationnel qui liste les procédures courantes avec les ordres_mission exactes. Conçu pour être lu pendant un incident, pas pour être étudié. Doit fonctionner à 2h du matin par quelqu'un de stressé. | `## Redémarrer le service` puis ordres_mission bash exactes avec résultat attendu et "si ça ne marche pas : voir section X" | Un protocole d'urgence médicale affiché sur le mur / le manuel du pilote pour les procédures d'urgence |
| **Squash merge** | Stratégie de merge qui combine tous les commits d'une branche en un seul avant de l'intégrer. Résultat : historique git propre, un commit par feature. Perte de l'historique détaillé de la branche. | `git merge --squash feature/vote-endpoint` : tous les commits "WIP", "fix", "fix 2" deviennent un seul "feat: add vote endpoint" | Résumer un long rapport en un paragraphe avant de le classer / distiller une semaine de travail en un seul livrable |
| **Technical debt** (dette technique) | Coût différé de mauvaises décisions de code. Comme une dette financière : elle s'accumule avec les intérêts (maintenance plus difficile, bugs plus fréquents) si on ne la rembourse pas. | `utils.js` de 1800 lignes : personne ne sait ce qui est utilisé, chaque modification prend 3x plus de temps = dette qui ralentit toute l'équipe | Un prêt contracté pour livrer vite qu'on rembourse plus tard en refactoring / une blessure mal soignée qui crée des complications chroniques |
| **Trunk-based development** | Stratégie de branches où tous les devs intègrent directement dans `main` plusieurs fois par jour avec de petites PRs. Opposé de Gitflow. Favorise l'intégration continue mais demande une forte culture de tests. | Chaque feature est une branche de 1 à 3 jours max, mergée dans `main` quand les tests passent. Pas de `develop`, pas de branches longues. | Un fleuve avec de nombreux affluents courts qui se rejoignent rapidement / une cuisine où chaque plat est servi dès qu'il est prêt |
| **Ubiquitous language** (DDD) | Vocabulaire commun partagé entre devs et experts métier. Les mêmes mots dans le code, les tickets, les réunions, et la doc. Évite les malentendus entre "vote" pour le métier et `ballot_entry` pour le dev. | Si le métier dit "vote", le code dit `vote` : classe `Vote`, fonction `registerVote`, table `votes`. Pas `ballot`, pas `entry`, pas `choice`. | Une langue commune dans une mission internationale / un dictionnaire partagé entre avocats et juges dans un tribunal |
