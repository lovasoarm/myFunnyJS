| Concept | Explication | Code (commenté) | Analogies |
|---|---|---|---|
| **API Gateway** | Point d'entrée unique pour toutes les requêtes vers tes microservices. Il authentifie, route, rate-limite, loggue : tout ça AVANT que ta vraie logique business voie quoi que ce soit. Un seul endroit pour tout contrôler, au lieu de répéter cette logique dans chaque service. | `// Le client tape toujours /api/*` <br>`// Le gateway décide qui répond` <br>`app.use('/api', (req, res, next) => {` <br>`  const key = req.headers['x-api-key'];` <br>`  if (!key || !isValid(key)) {` <br>`    return res.status(401).json({ error: 'Unauthorized' });` <br>`  }` <br>`  logger.info({ path: req.path, key });` <br>`  proxy.web(req, res, { target: routeTo(req.path) });` <br>`});` | Le vigile d'une boîte de nuit. Tu rentres pas directement dans la salle VIP : il vérifie ta liste, te fouille, te donne ton bracelet. Chaque salle derrière est un microservice différent. / Le standard téléphonique d'une grosse boîte. Tu appelles un seul numéro : lui sait si tu dois aller aux RH, à la compta ou au support. T'as jamais 5 numéros à retenir. |
| **Load Balancer** | Distribue le trafic entrant sur plusieurs instances d'un même service. L'objectif : aucun serveur ne crève sous la charge pendant que les autres tournent à 10%. Stratégies principales : round-robin, least connections, IP hash. | `const servers = ['srv1:3000', 'srv2:3000', 'srv3:3000'];` <br>`let index = 0;` <br>`function nextServer() {` <br>`  const srv = servers[index];` <br>`  index = (index + 1) % servers.length;` <br>`  // 0 -> 1 -> 2 -> 0 -> 1 -> 2 ...` <br>`  return srv;` <br>`}` <br>`app.use((req, res) => {` <br>`  proxy.web(req, res, { target: nextServer() });` <br>`});` | Un chef de caisse au supermarché. Quand une file explose, il ouvre une caisse supplémentaire et redirige les clients : pas par gentillesse, pour que le système tienne. / Un dispatcher de pizzas. 100 commandes, 4 livreurs. Il répartit 25 par livreur au lieu de tout balancer sur un seul qui finira par s'effondrer. |
| **Reverse Proxy** | Serveur intermédiaire qui reçoit les requêtes clients et les transmet aux serveurs backend. Le client ne sait jamais à quel serveur réel il parle. Bonus : SSL termination, compression, cache statique, protection DDoS. | `// Nginx (pseudo-code simplifié)` <br>`server {` <br>`  listen 443 ssl;` <br>`  server_name monsite.com;` <br>`  location / {` <br>`    proxy_pass http://localhost:3000; // backend caché` <br>`    proxy_set_header X-Real-IP $remote_addr;` <br>`    // Le backend voit l'IP réelle du client via header` <br>`  }` <br>`}` | Un agent littéraire. L'éditeur (client) envoie ses demandes à l'agent. L'agent dispatch à l'auteur (backend). L'éditeur ne sait jamais qui écrit, et l'auteur n'est jamais exposé directement. / Un service courrier entreprise. Tu envoies ton colis à "Bureau Paris". Le coursier interne choisit le bon étage, le bon bureau. Toi t'en sais rien, et c'est voulu. |
| **Rate Limiting** | Limite le nombre de requêtes qu'un client peut faire sur une période donnée. Protège contre les abus, les scrapers, les boucles infinies et le brute-force. Réponse standard quand la limite est atteinte : HTTP 429 Too Many Requests. | `const counts = new Map(); // ip -> { count, resetAt }` <br>`function rateLimiter(req, res, next) {` <br>`  const ip = req.ip;` <br>`  const now = Date.now();` <br>`  const entry = counts.get(ip) || { count: 0, resetAt: now + 60_000 };` <br>`  if (now > entry.resetAt) {` <br>`    entry.count = 0; entry.resetAt = now + 60_000;` <br>`  }` <br>`  entry.count++;` <br>`  counts.set(ip, entry);` <br>`  if (entry.count > 100) {` <br>`    return res.status(429).json({ error: 'Too Many Requests' });` <br>`  }` <br>`  next();` <br>`}` | Le videur qui compte les entrées. Passé 200 personnes dans la salle, tout le monde attend dehors même s'ils ont payé. La capacité maximale n'est pas négociable. / Un robinet avec minuterie. Tu peux prendre 10 litres par heure. T'en prends 10 en 2 minutes : il se coupe automatiquement jusqu'à la prochaine heure. |
| **Throttling** | Cousin du rate limiting, axé sur la **vitesse** plutôt que le comptage total. On ralentit le débit au lieu de bloquer net. Rate limiting dit "stop". Throttling dit "doucement". Implémentation classique : token bucket ou leaky bucket. | `class TokenBucket {` <br>`  constructor(capacity, refillRate) {` <br>`    this.tokens = capacity;` <br>`    this.capacity = capacity;` <br>`    // Régénère des tokens à intervalle fixe` <br>`    setInterval(() => {` <br>`      this.tokens = Math.min(this.capacity, this.tokens + 1);` <br>`    }, 1000 / refillRate);` <br>`  }` <br>`  consume() {` <br>`    if (this.tokens > 0) { this.tokens--; return true; }` <br>`    return false; // attends que des tokens se régénèrent` <br>`  }` <br>`}` | Autoroute avec vitesse dynamique. En heure de pointe les panneaux passent à 70km/h au lieu de 130. Tu roules toujours : le flux est régulé pour que personne s'écrase. / Un DJ qui baisse le BPM progressivement à 3h du mat. Il coupe pas la musique : il réduit l'intensité pour tenir la salle jusqu'à la fermeture. |
| **Pagination** | Découper un grand résultat en pages plutôt que de tout envoyer en une seule réponse. Stratégies : offset (classique, simple, lent sur gros volumes), cursor (performant, idéal pour les feeds). Ne jamais retourner 100 000 lignes en une réponse. | `app.get('/posts', async (req, res) => {` <br>`  const page = parseInt(req.query.page) || 1;` <br>`  const limit = parseInt(req.query.limit) || 20;` <br>`  const offset = (page - 1) * limit; // page 3 = skip 40` <br>`  const posts = await db.query(` <br>`    'SELECT * FROM posts ORDER BY id DESC LIMIT ? OFFSET ?',` <br>`    [limit, offset]` <br>`  );` <br>`  const total = await db.count('posts');` <br>`  res.json({ data: posts, page, limit, total });` <br>`});` | Un manga publié en volumes. Tu lis pas les 500 chapitres en une session : tome par tome. Si Shonen Jump te balançait tout en PDF d'un coup, ton téléphone mourrait. / Netflix et ses épisodes. Pas toute la saison dans un seul fichier de 20GB. Tu reçois un épisode, tu en demandes un autre. Géré côté serveur. |
| **Cache Stampede** | Bug catastrophique aussi appelé "thundering herd". Le cache expire, 10 000 requêtes arrivent en même temps, toutes vont interroger la BDD simultanément : la BDD s'effondre. Classique sur les pages les plus populaires à fort trafic. | `const locks = new Set();` <br>`async function getWithLock(key, fetchFn) {` <br>`  const cached = await redis.get(key);` <br>`  if (cached) return JSON.parse(cached); // cache hit, tout va bien` <br>`  if (locks.has(key)) {` <br>`    await sleep(50); // quelqu'un reconstruit déjà, attends` <br>`    return getWithLock(key, fetchFn); // réessaie` <br>`  }` <br>`  locks.add(key); // UNE SEULE requête va en BDD` <br>`  const data = await fetchFn();` <br>`  await redis.set(key, JSON.stringify(data), 'EX', 300);` <br>`  locks.delete(key);` <br>`  return data;` <br>`}` | 30 élèves qui se ruent vers la porte en même temps quand le prof dit "c'est fini". Tout le monde est bloqué. Si un seul ouvrait et que les autres attendaient leur tour, ça irait 10x plus vite. / Panneau "SOLDES 70%" qui s'affiche à minuit. 50 000 personnes refresh simultanément. Le cache venait d'expirer. Le site crash. Les soldes commencent sans site. |
| **Idempotency** | Une opération idempotente produit le même résultat peu importe combien de fois tu l'exécutes. GET est idempotent. PUT est idempotent. POST en général pas. Critique pour les paiements et les emails : si le réseau coupe après envoi, le client peut retry sans risque de doublon. | `app.post('/payment', async (req, res) => {` <br>`  const { idempotencyKey, amount, userId } = req.body;` <br>`  const existing = await db.payments.findOne({ idempotencyKey });` <br>`  if (existing) {` <br>`    // Déjà traité : même résultat, aucun 2ème débit` <br>`    return res.json({ status: 'already_processed', data: existing });` <br>`  }` <br>`  const payment = await stripe.charge({ amount, userId });` <br>`  await db.payments.save({ idempotencyKey, ...payment });` <br>`  res.json({ status: 'success', data: payment });` <br>`});` | Appuyer sur le bouton d'ascenseur déjà allumé. T'appuies 10 fois : l'ascenseur vient une seule fois. Le 11ème appui ne crée pas 11 ascenseurs. / Supprimer un fichier qui n'existe plus. La commande réussit quand même (ou répond "already gone") : elle ne plante pas et ne supprime pas deux fois. |
| **GraphQL** | Langage de requête pour API où le **client** choisit exactement les données qu'il veut. Fini l'over-fetching (100 champs reçus pour en utiliser 3) et l'under-fetching (1 requête ne suffit pas, on en chaîne 5). Un seul endpoint `/graphql`, des requêtes déclaratives. | `const query = \`` <br>`  query {` <br>`    user(id: "42") {` <br>`      name` <br>`      email` <br>`      # On demande PAS le mot de passe, l'adresse, les logs` <br>`      posts(limit: 5) {` <br>`        title` <br>`        publishedAt` <br>`        # On demande PAS le contenu entier` <br>`      }` <br>`    }` <br>`  }` <br>`\`;` <br>`const res = await fetch('/graphql', {` <br>`  method: 'POST',` <br>`  body: JSON.stringify({ query }),` <br>`  headers: { 'Content-Type': 'application/json' },` <br>`});` | Commander à la carte. Avec REST c'est menu fixe : tu prends tout ou rien, même ce que tu veux pas. GraphQL c'est "juste l'entrée et le dessert, sans le plat". Le serveur t'apporte exactement ça. / Un formulaire douanier que tu remplis toi-même. Tu coches exactement ce que tu transportes. Le douanier REST ouvre toute ta valise pour un seul objet : perte de temps des deux côtés. |
| **gRPC** | Framework RPC de Google utilisant Protocol Buffers (format binaire, pas JSON). Ultra-rapide, fortement typé, HTTP/2 natif. Pensé pour la communication entre microservices où la performance compte plus que la lisibilité humaine. Le contrat est défini dans un fichier `.proto`. | `// users.proto : le contrat entre services` <br>`// syntax = "proto3";` <br>`// service UserService {` <br>`//   rpc GetUser (UserRequest) returns (UserResponse);` <br>`//   rpc ListUsers (ListRequest) returns (stream UserResponse);` <br>`// }` <br>`// Côté client Node.js` <br>`const client = new UserServiceClient(` <br>`  'auth-service:50051',` <br>`  credentials.createInsecure()` <br>`);` <br>`client.getUser({ id: '42' }, (err, response) => {` <br>`  // response est fortement typé, pas un JSON balade` <br>`  console.log(response.name);` <br>`});` | Deux ingénieurs qui échangent des schémas techniques au lieu de se parler en langage courant. Plus précis, plus rapide, incompréhensible pour un humain lambda : c'est exactement le but. / Un contrat notarié signé avant toute communication. Les deux services ont signé un `.proto` qui dit exactement quels messages ils s'envoient. Aucune surprise possible, aucune ambiguïté. |
| **Webhooks** | Inverse du polling. Au lieu que ton app demande "t'as du nouveau ?" en boucle, le serveur **te pousse** une notification HTTP dès qu'un événement se passe. Tu enregistres ton URL, tu attends, tu reçois. Beaucoup plus efficace que de poller toutes les X secondes. | `app.post('/webhooks/stripe', express.raw({ type: 'application/json' }), (req, res) => {` <br>`  const sig = req.headers['stripe-signature'];` <br>`  // Vérifie que c'est bien Stripe qui envoie, pas un imposteur` <br>`  const event = stripe.webhooks.constructEvent(req.body, sig, process.env.STRIPE_SECRET);` <br>`  switch (event.type) {` <br>`    case 'payment_intent.succeeded':` <br>`      activatePremium(event.data.object.customer); break;` <br>`    case 'customer.subscription.deleted':` <br>`      revokePremium(event.data.object.customer); break;` <br>`  }` <br>`  res.status(200).send('OK'); // toujours répondre 200 vite` <br>`});` | Une sonnette de porte vs regarder par la fenêtre toutes les 10 secondes. Le webhook c'est la sonnette : quelqu'un appuie, tu es notifié immédiatement. Le polling c'est toi qui surveilles seul, en continu, pour rien. / S'abonner à une newsletter. Tu donnes ton email (URL), l'auteur t'envoie un email (POST) quand il publie. Tu ne demandes rien : ça arrive. C'est lui qui pousse vers toi. |
| **JWT** | JSON Web Token. Jeton signé encodé en base64 contenant des claims (infos utilisateur). Le serveur signe à la création, le client stocke et renvoie à chaque requête. Stateless : aucun état côté serveur. La signature cryptographique garantit que personne n'a modifié le payload en transit. | `// Génération au login` <br>`const token = jwt.sign(` <br>`  { userId: 42, role: 'admin', plan: 'pro' },` <br>`  process.env.JWT_SECRET,` <br>`  { expiresIn: '1h' }` <br>`);` <br>`// Vérification à chaque requête protégée` <br>`function authMiddleware(req, res, next) {` <br>`  const token = req.headers.authorization?.split(' ')[1];` <br>`  const decoded = jwt.verify(token, process.env.JWT_SECRET);` <br>`  // decoded.userId = 42 : SANS toucher la BDD` <br>`  req.user = decoded;` <br>`  next();` <br>`}` | Un bracelet VIP de festival. Le staff le crée à l'entrée, tu le portes toute la journée. Chaque stand vérifie juste le bracelet : personne ne rappelle le guichet d'entrée pour confirmer à chaque fois. / Un passeport. Il contient tes infos, signé par l'État (serveur). À chaque douane (endpoint protégé), on vérifie la signature : pas le dossier complet. |
| **OAuth** | Protocole d'autorisation. Permet à une app d'accéder à tes ressources chez un tiers (Google, GitHub, Discord) **sans jamais voir ton mot de passe**. Le flow échange un code contre un token d'accès à portée limitée (scope). | `// Étape 1 : redirige l'utilisateur vers le provider` <br>`const params = new URLSearchParams({` <br>`  client_id: process.env.GOOGLE_CLIENT_ID,` <br>`  redirect_uri: 'http://localhost:3000/auth/callback',` <br>`  response_type: 'code',` <br>`  scope: 'email profile', // accès limité, rien d'autre` <br>`});` <br>`res.redirect(\`https://accounts.google.com/o/oauth2/v2/auth?\${params}\`);` <br>`// Étape 2 : callback avec le code` <br>`app.get('/auth/callback', async (req, res) => {` <br>`  const { access_token } = await exchangeCode(req.query.code);` <br>`  const profile = await fetchGoogleProfile(access_token);` <br>`});` | Donner les clés de ta voiture au voiturier. Tu lui confies uniquement la clé de voiture (scope limité) : pas ta carte bancaire, pas les clés de ta maison. Il gare la voiture, rien d'autre. / Faire une procuration pour récupérer un colis à la Poste. Tu donnes un mandat précis (token scoped) : récupérer CE colis spécifique, pas ouvrir tout ton compte. |
| **Cache Invalidation** | Quand et comment supprimer ou mettre à jour les données en cache quand la source de vérité change. Stratégies : TTL (expiration auto), write-through (cache + BDD mis à jour ensemble), event-driven (un event déclenche l'invalidation). Phil Karlton : "There are only two hard things in CS: cache invalidation and naming things." | `// Write-through : cache et BDD toujours synchronisés` <br>`async function updateUser(id, newData) {` <br>`  await db.users.update(id, newData);` <br>`  await redis.set(\`user:\${id}\`, JSON.stringify(newData), 'EX', 3600);` <br>`}` <br>`// Invalidation : on supprime, le prochain GET recharge depuis la BDD` <br>`async function invalidateUser(id) {` <br>`  await redis.del(\`user:\${id}\`);` <br>`  // La prochaine lecture ira en BDD et reconstruira le cache` <br>`}` <br>`// Erreur classique : mettre à jour la BDD sans toucher le cache` <br>`// -> données périmées servies pendant des heures` | Tableau d'affichage dans un couloir. Les étudiants lisent le tableau (cache). Si le cours change de salle et que tu oublies de mettre à jour l'affichage, ils arrivent en 204 alors que c'est en 108. / Un GPS avec carte offline. La carte c'est le cache. Une nouvelle autoroute ouvre et tu mets pas à jour : le GPS t'envoie dans un champ. |
| **Composite Index** | Index de BDD créé sur **plusieurs colonnes combinées**. Accélère massivement les requêtes qui filtrent sur ces colonnes ensemble. L'ordre des colonnes est critique : un index `(a, b)` aide une requête sur `a` seul, mais pas sur `b` seul. | `-- Sans index : full table scan sur 50 millions de lignes` <br>`SELECT * FROM orders WHERE user_id = 42 AND status = 'pending';` <br>`-- Avec composite index : saut direct` <br>`CREATE INDEX idx_user_status ON orders(user_id, status);` <br>`-- Comprendre l'ordre (index sur user_id, status) :` <br>`--   OK : WHERE user_id = 42 AND status = 'pending'` <br>`--   OK : WHERE user_id = 42 (colonne 1 seule)` <br>`--   PAS OK : WHERE status = 'pending' (colonne 2 seule : full scan)` <br>`-- EXPLAIN ANALYZE pour vérifier ce que la BDD fait vraiment` | Un annuaire trié par NOM puis PRÉNOM. Chercher "Dupont Jean" : direct. Chercher tous les "Jean" toutes familles confondues : tu dois tout parcourir depuis le début. L'index aide dans un sens seulement. / Un classeur de factures rangé par ANNÉE puis CLIENT. Trouver "2024, Prometheus" : instantané. Trouver tout ce qui concerne Prometheus toutes années confondues : tu ouvres chaque classeur un par un. |
| **Query Optimization** | L'art de réécrire ou structurer une requête SQL pour qu'elle soit le plus rapide possible. Armes principales : EXPLAIN ANALYZE, JOIN au lieu de boucles, sélectionner uniquement les colonnes nécessaires, index bien placés. La pire erreur courante : le problème N+1. | `// N+1 : 1 query pour 100 users + 100 queries pour leurs posts` <br>`const users = await db.query('SELECT * FROM users LIMIT 100');` <br>`for (const u of users) {` <br>`  // 1 requête par user -> 100 aller-retours en BDD` <br>`  u.posts = await db.query('SELECT * FROM posts WHERE user_id = ?', [u.id]);` <br>`}` <br>`// Optimisé : 1 seul aller-retour` <br>`const result = await db.query(\`` <br>`  SELECT u.id, u.name, p.title, p.created_at` <br>`  FROM users u` <br>`  LEFT JOIN posts p ON p.user_id = u.id` <br>`  WHERE u.active = true LIMIT 100` <br>`\`);` | Un cuisinier qui fait 50 voyages au frigo, un ingrédient à la fois. vs un cuisinier qui sort tout ce dont il a besoin avant de commencer. Même résultat, temps radicalement différent. / Chercher 50 mots dans un dictionnaire un par un vs faire la liste d'abord et chercher tous en ordre alphabétique en une session. Donne à la BDD le moins d'aller-retours possible. |
| **CAP Theorem** | Un système distribué ne peut garantir simultanément que 2 de ces 3 propriétés : **C**onsistency (toujours la donnée la plus récente), **A**vailability (toujours une réponse), **P**artition Tolerance (résiste aux coupures réseau). En prod, P est obligatoire : tu choisis entre CP et AP. | `// CP : cohérence prioritaire sur disponibilité` <br>`// MongoDB en mode strict :` <br>`// Si le noeud primaire est isolé du réseau,` <br>`// le cluster refuse les écritures` <br>`// plutôt que de risquer des données incohérentes.` <br>`// AP : disponibilité prioritaire sur cohérence` <br>`// Cassandra, DynamoDB :` <br>`// Si un noeud est coupé, il continue à répondre` <br>`// avec des données potentiellement en retard.` <br>`// Deux noeuds peuvent avoir des valeurs différentes temporairement.` <br>`// Pas de bon choix absolu : ça dépend de ton use case.` | Deux colocataires. L'un est toujours fiable mais parfois absent (CP). L'autre est toujours là mais pas toujours fiable (AP). Quand le réseau coupe, tu ne peux pas avoir les deux à la fois. T'as un choix à faire avant la panne. / Groupe WhatsApp sans réseau. Soit tout le monde attend la reconnexion avant d'envoyer (CP). Soit certains envoient offline et les messages arrivent dans le désordre (AP). Aucune option n'est gratuite. |
| **ACID** | Propriétés des transactions dans les BDD relationnelles. **A**tomicité (tout ou rien : une étape plante, tout est annulé), **C**onsistance (les contraintes de la BDD restent respectées), **I**solation (les transactions simultanées ne s'interfèrent pas), **D**urabilité (une transaction committée survit même à un crash). | `-- Virement bancaire : l'exemple canonique` <br>`BEGIN TRANSACTION;` <br>`  UPDATE accounts` <br>`  SET balance = balance - 100` <br>`  WHERE id = 1 AND balance >= 100;` <br>`  UPDATE accounts` <br>`  SET balance = balance + 100` <br>`  WHERE id = 2;` <br>`  -- Si une des deux lignes plante : ROLLBACK automatique` <br>`  -- Jamais de débit sans crédit en base` <br>`COMMIT;` | Un distributeur de billets. Il te donne 200€ et débite ton compte en même temps. Si la machine plante entre les deux, la transaction est annulée : tu perds pas 200€ dans le vide. / Un déménagement tout-ou-rien. Soit tous les cartons arrivent dans le nouvel appart, soit on remet tout dans l'ancien. Pas de "moitié ici, moitié là-bas". |
| **Sharding** | Partitionnement horizontal d'une BDD. Les données sont découpées en morceaux (shards) distribués sur plusieurs machines. Chaque shard ne contient qu'une partie des données. Obligatoire quand une seule machine ne peut plus tenir le volume. La shard key détermine où chaque donnée atterrit. | `const SHARD_COUNT = 4;` <br>`function getShard(userId) {` <br>`  return userId % SHARD_COUNT;` <br>`  // user 40 -> shard 0` <br>`  // user 41 -> shard 1` <br>`  // user 42 -> shard 2` <br>`  // user 43 -> shard 3, user 44 -> shard 0 (cycle)` <br>`}` <br>`async function getUser(userId) {` <br>`  const shardIndex = getShard(userId);` <br>`  const db = shardConnections[shardIndex]; // serveur différent par shard` <br>`  return db.query('SELECT * FROM users WHERE id = ?', [userId]);` <br>`}` | Une bibliothèque géante divisée en 4 annexes par thème. Romans ici, sciences là, histoire ailleurs. Moins de monde dans chaque, recherche plus rapide, aucun bâtiment saturé. / Une ville qui ouvre plusieurs bureaux de poste au lieu d'un seul central. Chaque bureau gère son quartier. Personne ne fait 20km pour un colis : la charge est distribuée. |
| **Circuit Breaker** | Pattern de résilience. Quand un service downstream échoue trop souvent, on "ouvre le circuit" : on arrête d'appeler, on répond immédiatement en erreur (fail fast). Après un délai, on réessaie prudemment (half-open). Évite les cascades de pannes où un service mort tue tout le système. | `class CircuitBreaker {` <br>`  constructor(threshold = 5, timeout = 30_000) {` <br>`    this.failures = 0; this.threshold = threshold;` <br>`    this.timeout = timeout; this.state = 'CLOSED';` <br>`    this.nextAttempt = null;` <br>`  }` <br>`  async call(fn) {` <br>`    if (this.state === 'OPEN') {` <br>`      if (Date.now() < this.nextAttempt) throw new Error('Circuit OPEN');` <br>`      this.state = 'HALF_OPEN'; // on tente prudemment` <br>`    }` <br>`    try {` <br>`      const result = await fn();` <br>`      this.failures = 0; this.state = 'CLOSED';` <br>`      return result;` <br>`    } catch (e) {` <br>`      this.failures++;` <br>`      if (this.failures >= this.threshold) {` <br>`        this.state = 'OPEN';` <br>`        this.nextAttempt = Date.now() + this.timeout;` <br>`      }` <br>`      throw e;` <br>`    }` <br>`  }` <br>`}` | Le disjoncteur électrique chez toi. Trop d'appareils branchés en même temps : ça claque. Au lieu de cramer toute l'installation, le disjoncteur coupe. T'attends, tu réenclenches, tu surveilles. / Un médecin qui prescrit "repos complet 3 semaines" après une blessure. Le circuit (toi) est ouvert. Après la période de recovery, on réessaie progressivement : pas question de courir le lendemain. |
| **Livelock** | Deux processus se modifient mutuellement en réponse l'un à l'autre, sans jamais avancer. Contrairement au deadlock où tout est gelé, dans un livelock tout le monde "bouge" : mais le mouvement ne produit aucun progrès. Les deux se cèdent mutuellement en boucle infinie. | `// Les deux processus se "cèdent" mutuellement à l'infini` <br>`async function processX() {` <br>`  while (true) {` <br>`    resourceA = 'X';` <br>`    if (resourceB !== 'free') {` <br>`      resourceA = 'free'; // cède si B pas dispo` <br>`      await sleep(10); // réessaie` <br>`      continue;` <br>`    }` <br>`    resourceB = 'X'; break; // enfin les deux` <br>`  }` <br>`}` <br>`// processY fait exactement pareil -> boucle infinie de politesse` <br>`// Solution : random backoff avant retry` <br>`await sleep(Math.random() * 100 + 10);` | Deux personnes dans un couloir étroit qui s'écartent du même côté à chaque fois. Aucune n'est bloquée physiquement : mais personne n'avance. Le mouvement lui-même est devenu le problème. / Deux voitures à une intersection sans priorité qui s'arrêtent toutes les deux pour laisser passer l'autre. Poliment. À jamais. Solution : l'une attend un délai aléatoire et part en premier. |
| **CSRF** | Cross-Site Request Forgery. Un site malveillant forge une requête vers ton app depuis le navigateur d'un utilisateur connecté. Le navigateur envoie automatiquement les cookies de session : la requête arrive authentifiée sans que l'utilisateur l'ait voulue. | `const csrf = require('csurf');` <br>`app.use(csrf({ cookie: true })); // génère un token unique par session` <br>`// Formulaire : injecte le token dans le HTML` <br>`app.get('/transfer', (req, res) => {` <br>`  res.render('transfer', { csrfToken: req.csrfToken() });` <br>`  // <input type="hidden" name="_csrf" value="TOKEN">` <br>`});` <br>`// Validation : csurf vérifie automatiquement` <br>`app.post('/transfer', (req, res) => {` <br>`  // Token absent ou invalide -> 403 automatique` <br>`  processTransfer(req.body);` <br>`  res.json({ status: 'done' });` <br>`});` | Quelqu'un signe un chèque à ton nom pendant que t'as le dos tourné : pas besoin de ton mot de passe, juste de ton carnet laissé sur la table et de ta signature visible. / Un faux bouton "confirmer" dans un mail d'apparence légitime. Tu cliques, tu viens d'autoriser un virement depuis ta session encore active. Ton mot de passe n'a jamais été demandé. |
| **Backpressure** | Mécanisme qui ralentit le producteur quand le consommateur ne peut plus suivre. Sans backpressure : le producteur inonde le buffer, la mémoire explose, le process crash. Avec backpressure : le producteur attend que le consommateur soit prêt avant d'envoyer plus. Critique dans les streams et pipelines de données. | `const readable = fs.createReadStream('huge-file.csv');` <br>`const writable = fs.createWriteStream('output.csv');` <br>`// pipe() gère la backpressure automatiquement` <br>`readable.pipe(writable);` <br>`// Pour comprendre le mécanisme :` <br>`readable.on('data', (chunk) => {` <br>`  const canContinue = writable.write(chunk);` <br>`  if (!canContinue) {` <br>`    readable.pause(); // STOP : consommateur saturé` <br>`    writable.once('drain', () => {` <br>`      readable.resume(); // OK : consommateur a vidé son buffer` <br>`    });` <br>`  }` <br>`});` | Un tuyau d'arrosage relié à une pompe industrielle. Si tu ouvres à fond sans régulateur, le tuyau explose. Le régulateur de pression (backpressure) s'assure que le débit reste dans ce que le tuyau peut encaisser. / Un convoyeur de colis qui ralentit automatiquement quand la zone d'emballage est pleine. La production ne s'arrête pas : elle se synchronise avec la capacité de traitement en aval. |
| **False Sharing** | Bug de performance dans le code multi-threadé. Deux threads modifient des variables **différentes** qui tombent dans la même ligne de cache CPU (64 bytes). À chaque modification, le CPU invalide la ligne entière pour tous les autres coeurs : contention et dégradation de performance sans raison apparente. | `// C++ pour illustrer (concept identique en Java, Rust, Go)` <br>`struct Counter {` <br>`  int x; // thread 1 écrit ici` <br>`  int y; // thread 2 écrit ici` <br>`  // x et y sont côte à côte : même cache line de 64 bytes` <br>`  // Modifier x invalide y pour le thread 2, et inversement` <br>`  // Résultat : cache bouncing constant entre les 2 coeurs` <br>`};` <br>`// Solution : padding pour forcer chaque var dans sa propre cache line` <br>`struct CounterFixed {` <br>`  int x;` <br>`  char pad[60]; // occupe le reste des 64 bytes` <br>`  int y;        // maintenant dans une cache line distincte` <br>`};` | Deux collègues qui partagent un seul tiroir avec une seule clé. Même s'ils travaillent sur des dossiers complètement différents, chaque fois que l'un ouvre, l'autre attend. La clé est partagée inutilement. / Deux musiciens qui jouent des instruments différents rangés dans le même étui. Chaque fois que l'un veut répéter, l'autre ne peut pas accéder au sien. Problème d'organisation, pas de compétition réelle. |
| **mTLS** | Mutual TLS. Extension du TLS classique où **les deux côtés** s'authentifient avec des certificats. En TLS normal, seul le serveur prouve son identité. En mTLS, le client aussi. Indispensable entre microservices dans une architecture zero-trust : personne n'est de confiance par défaut, même à l'intérieur du réseau. | `// Serveur Node.js avec mTLS activé` <br>`const server = https.createServer({` <br>`  key: fs.readFileSync('server-key.pem'),` <br>`  cert: fs.readFileSync('server-cert.pem'),` <br>`  ca: fs.readFileSync('ca-cert.pem'),   // autorité commune` <br>`  requestCert: true,                    // exige le cert du client` <br>`  rejectUnauthorized: true              // refuse si cert invalide` <br>`}, app);` <br>`// Client : doit fournir son propre certificat` <br>`const response = await fetch('https://auth-service/', {` <br>`  agent: new https.Agent({` <br>`    key: fs.readFileSync('client-key.pem'),` <br>`    cert: fs.readFileSync('client-cert.pem'),` <br>`    ca: fs.readFileSync('ca-cert.pem'),` <br>`  })` <br>`});` | Contrôle de sécurité niveau ambassade. Tu montres ton passeport (TLS normal) : l'agent vérifie TON identité. En mTLS, l'agent montre aussi son badge officiel avant de t'adresser la parole. Vérification mutuelle dans les deux sens. / Poignée de main secrète dans une fraternité. Les deux membres doivent connaître la séquence complète. Si l'un rate une étape : la porte reste fermée. Aucune confiance implicite, jamais. |
